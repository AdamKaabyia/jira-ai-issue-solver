3. How the LLM Is Used

Key insight: No multi-agent orchestration

The bot does not implement chains, RAG, or multi-agent patterns. It makes exactly one CLI invocation per job: start the AI CLI, give it a task file, wait for it to finish, collect the results.

LLM Flow Single AI Session
A
Bot writes task files
.ai-session/task.md — "Implement CERTPX-17737: GPUVendorDetector extensions. Validate your changes compile and pass tests."
.ai-session/issue.md — Full Jira ticket description, acceptance criteria, file hints.
Generated by taskfile/ package. Includes per-repo instructions + workflow overrides from profiles.
B
Bot starts a container
podman run -d --pull=never ghcr.io/zeroae/claude-code:latest sleep infinity
Mounts your workspace at /workspace. Sets env vars for AI authentication.
Defined in container/runtime_manager.go.
C
AI Execution One CLI command
Claude:
claude --dangerously-skip-permissions --output-format json --verbose -p "Read /workspace/.ai-session/task.md and complete the task described there."

Gemini:
gemini -y --output-format json -p "Read /workspace/.ai-session/task.md and complete the task described there."

Defined in executor/script.go. The CLI tool is itself an autonomous agent — it reads files, edits code, runs tests inside the container. But the bot treats it as a black-box subprocess.
D
Bot collects output
Reads .ai-session/session-output.json for exit code and cost.
Reads .ai-session/cli-output.json for token counts.
Reads .ai-session/pr.md (if present) for AI-generated MR description.
Checks git status for changed files.
E
Bot commits and creates MR
Pushes changes via git push with authenticated URL.
Creates a Merge Request via the GitLab API.
Posts the MR link as a Jira comment, transitions ticket to "in review".

4. New-Ticket Pipeline (17 Steps)

Pipeline Full step-by-step for executeNewTicket()
  1. Fetch work item details from Jira (GET /issue/{key})
  2. Resolve project settings: which repo, status names, profiles, container image
  3. Validate fork-mode requirements and per-ticket cost cap
  4. Transition ticket to in-progress status (POST /transitions)
  5. Prepare workspace: git clone the repo (or reuse existing)
  6. Create branch: git checkout -b ai-bot/CERTPX-17737
  7. Load repo config: reads .ai-bot/config.yaml from the cloned repo
  8. Clone imports: auxiliary repos for shared tools/context
  9. Write .ai-session/issue.md and .ai-session/task.md
  10. Determine AI provider: project setting → default from config
  11. Build AI CLI command (executor/script.go)
  12. Pull container image + start container with sleep infinity
  13. Run import install commands inside container
  14. Strip remote auth from .git/config (prevent AI from pushing)
  15. Execute AI CLI inside container — this is the single LLM invocation
  16. Restore remote auth, commit changes via git push
  17. Create Merge Request, update Jira ticket with MR link, transition to in-review
Pipeline Feedback pipeline (when reviewers comment on MR)
  1. Fetch ticket + resolve project settings
  2. Find open MR by branch name (ai-bot/CERTPX-17737)
  3. Find or recreate workspace (self-healing if cleaned up)
  4. Switch to MR branch, sync with remote
  5. Fetch MR comments, filter bot-authored and ignored users
  6. Write feedback task file with review comments
  7. Resolve container, execute AI, check for changes
  8. Commit changes via git push
  9. Reply to addressed MR comments

Key difference: no branch creation, no MR creation, no status transition. Reuses existing workspace and MR.

5. Your Current Failure

Claude Code refused to run — container runs as root

The session.log from your CERTPX-17737 run contains exactly one line:

--dangerously-skip-permissions cannot be used with root/sudo privileges for security reasons

What happened:

  • ghcr.io/zeroae/claude-code:latest runs the container process as root (UID 0).
  • Claude Code CLI has a safety check that blocks --dangerously-skip-permissions when running as root.
  • The CLI exited immediately with exit code 1. Zero tokens consumed (cost_usd: 0).
  • The only "changes" were the .ai-session/ metadata files (task.md, issue.md, etc.).
  • The bot saw those as changes, committed them, and created MR #1752 with no actual code.

Fix: The container must run the Claude Code CLI as a non-root user. Options:
• Build a custom image with a non-root user (e.g., USER node in Dockerfile)
• Use podman run --user 1000:1000 (configure via container settings in config.yaml)
• Find/use an image that already runs as non-root

6. AI Authentication Paths

The bot sets environment variables inside the container. The AI CLI reads them to know where to send API requests. Here are all supported paths:

Auth Direct Anthropic API key

Simplest mode. Requires a direct Anthropic API key.

# config.yaml
claude:
  api_key: "sk-ant-..."

Container env: ANTHROPIC_API_KEY=sk-ant-...

Claude Code CLI calls api.anthropic.com directly.

Auth Google Vertex AI (GCP credentials)

Uses a GCP service account key file, mounted into the container.

# config.yaml
claude:
  vertex_project_id: "my-gcp-project"
  vertex_region: "us-east5"
  vertex_credentials_file: "/path/to/sa-key.json"

Container env: CLAUDE_CODE_USE_VERTEX=1, GOOGLE_APPLICATION_CREDENTIALS=/run/secrets/gcp-sa-key.json

The key file is mounted read-only at /run/secrets/gcp-sa-key.json.

Auth API Proxy (e.g., Models.corp) — your setup

Routes requests through a corporate proxy that handles upstream auth. Two sub-modes:

Non-Vertex format (simple proxy)

# config.yaml
claude:
  proxy_url: "https://my-proxy.corp.com"
  proxy_auth_token: "bearer-token-here"

Container env: ANTHROPIC_BASE_URL=https://my-proxy.corp.com, ANTHROPIC_AUTH_TOKEN=bearer-token-here

Vertex format (Models.corp with URL translation)

# config.yaml
claude:
  proxy_url: "https://models.corp.redhat.com"
  proxy_auth_token: "bearer-token-here"
  proxy_vertex_format: true
  vertex_project_id: "placeholder"
  vertex_region: "placeholder"

The bot starts a local URL translation proxy (proxy/proxy.go) that:

  • Listens on localhost:<random-port>
  • Rewrites Claude Code's Vertex AI paths to Models.corp's custom format (proxy/rewrite.go)
  • Adds the Authorization: Bearer header to upstream requests

Container env: ANTHROPIC_VERTEX_BASE_URL=http://aiproxy:<port>, CLAUDE_CODE_SKIP_VERTEX_AUTH=1

Container gets --add-host aiproxy:host-gateway so it can reach the host proxy.

Auth Gemini API key 
# config.yaml
ai_provider: "gemini"
gemini:
  api_key: "AIza..."
  model: "gemini-2.5-pro"

Container env: GEMINI_API_KEY=AIza...

Gemini CLI uses OpenAI-compatible chat/completions format.

7. Using a Locally Hosted Model

Local model = point the AI CLI at your own server

The bot itself never calls the AI API. It sets env vars, and the CLI inside the container reads them. So "use a local model" means: run a model server on your machine and tell the CLI to use it instead of the cloud.

Option A Ollama / vLLM with Anthropic-compatible API

If your local server implements the Anthropic Messages API (POST /v1/messages):

# Start your local model server
# e.g., ollama with anthropic-compatible endpoint on port 11434

# config.yaml
ai_provider: "claude"
claude:
  proxy_url: "http://host.containers.internal:11434"
  proxy_auth_token: "dummy"
  proxy_vertex_format: false

This sets ANTHROPIC_BASE_URL=http://host.containers.internal:11434 inside the container. Claude Code CLI sends all requests there instead of api.anthropic.com.

Requirement: Your server must implement streaming SSE responses in the Anthropic Messages API format.

Network flow: 
Container (claude CLI)
  → http://aiproxy:PORT  (URL translation proxy on host, if vertex_format)
    → http://localhost:11434  (your local model server)

OR (without vertex_format):

Container (claude CLI)
  → http://host.containers.internal:11434  (direct to local server)
Option B OpenAI-compatible server (via Gemini path)

If your local server implements the OpenAI chat completions API (POST /v1/chat/completions):

# config.yaml
ai_provider: "gemini"
gemini:
  api_key: "dummy"
  model: "your-local-model-name"

The Gemini CLI reads GEMINI_API_KEY and uses the OpenAI-compatible format. You would need to also set the base URL inside the container image or via environment variable overrides.

Caveat: The Gemini CLI may have specific expectations about response format that simpler servers don't satisfy. The Claude path (Option A) is more proven.

Option C Fully custom provider

Build your own container image with a CLI tool that:

  1. Reads /workspace/.ai-session/task.md
  2. Calls your local model API however you want
  3. Edits files in /workspace/
  4. Exits with code 0 on success
# config.yaml
ai_provider: "my-tool"

The bot's fallback command is: my-tool -p "Read /workspace/.ai-session/task.md and complete the task described there."

This gives you total control. Any language, any model, any API.

9. How the AI Edits Code

The AI CLI is itself an autonomous agent

Claude Code CLI and Gemini CLI are not simple prompt→response tools. They are agentic loops with built-in tools: Read files, Edit files, run Bash commands, search code, and more. The bot treats them as a black-box subprocess, but inside the container, the AI is autonomously navigating the codebase, running tests, and iterating on its solution.

The exact CLI command

From executor/script.go, the bot constructs a bash script that runs inside the container:

# Claude provider
claude --dangerously-skip-permissions --output-format json --verbose \
  -p "Read /workspace/.ai-session/task.md and complete the task described there." \
  > /workspace/.ai-session/cli-output.json \
  2> >(tee /workspace/.ai-session/session.log >&2)
AI_EXIT=${PIPESTATUS[0]}
printf '{"exit_code": %d}\n' "$AI_EXIT" > /workspace/.ai-session/session-output.json
exit ${AI_EXIT}

# Gemini provider
gemini -y --output-format json \
  -p "Read /workspace/.ai-session/task.md and complete the task described there." \
  > /workspace/.ai-session/cli-output.json \
  2> >(tee /workspace/.ai-session/session.log >&2)
# ... same exit code handling

What the AI CLI does internally

1
Reads the task file
The prompt says "Read /workspace/.ai-session/task.md and complete the task". The CLI uses its Read tool to open this file and understand the assignment.
2
Explores the codebase
Uses Bash (find, grep, ls), Read, and search tools to understand the project structure, locate relevant files, and read existing code.
3
Edits files directly
Uses the Edit tool to make targeted changes to source files. Each edit specifies old content and new content — the CLI applies it like a surgical patch, not a full file rewrite.
4
Runs build & tests
Uses Bash to run make build, go test, npm test, or whatever the project uses. If tests fail, it reads the output, diagnoses the issue, and iterates.
5
Iterates until done
The agentic loop continues: edit → test → read errors → fix → retest. The loop ends when the AI considers the task complete, or the context window fills up, or the container times out.
6
Writes PR description (optional)
If the task file or workflow instructs it, the AI writes .ai-session/pr.md with a title and summary. The bot reads this file after the session ends.

Available tools inside the CLI

Tool Read
Read any file in the workspace
Tool Edit
Surgical find-and-replace edits
Tool Write
Create new files
Tool Bash
Run shell commands (build, test, grep)
Tool Search
Grep/find across the codebase

10. Improving Code Quality

Progressive enhancement — start simple, add layers as needed

Code quality from the AI is directly proportional to how much guidance you give it. Each level below adds a new configuration file to your target repository's .ai-bot/ directory. You don't need all of them — even Level 1 alone is a massive improvement.

1 .ai-bot/instructions.md — Universal instructions Biggest impact

This file is appended to every task file (both new tickets and PR feedback). It tells the AI how to validate its work and what coding standards to follow.

Why it matters: Without this file, the AI has to guess how to build and test your project. It might run the wrong commands, miss linting rules, or skip validation entirely. With this file, the AI knows exactly what commands to run and what standards to follow.

Example content

After making changes, validate with:
- `make build`    # must compile cleanly
- `make test`     # all tests must pass
- `make lint`     # no linting errors

Follow the existing code style in the repository.
Add unit tests for all new functions.
Do not modify generated files (*.pb.go, *_generated.go).
Keep commits atomic — one logical change per commit.

When fixing bugs, write a regression test first that
reproduces the failure, then implement the fix.

Placement: your-repo/.ai-bot/instructions.md

Applies to: All task types (new tickets + feedback)

2 .ai-bot/new-ticket-workflow.md — Structured multi-phase workflow

Guides the AI through a structured problem-solving process for new tickets. The AI follows explicit phases instead of ad-hoc coding.

Why it matters: Without a workflow, the AI jumps straight to coding. With one, it assesses the problem, diagnoses root causes, implements a fix, tests it, and self-reviews — like a disciplined developer would.

Example content

Execute the following bugfix workflow phases in order.
Each phase is defined in the corresponding skill file.

1. Read and execute .ai-workflows/bugfix/skills/assess.md
   The bug report is in .ai-session/task.md.
   Do not ask clarifying questions.

2. Read and execute .ai-workflows/bugfix/skills/diagnose.md
   Write root cause analysis to .ai-session/diagnosis.md.

3. Read and execute .ai-workflows/bugfix/skills/fix.md
   Implement the minimal fix. Do not run tests yet.

4. Read and execute .ai-workflows/bugfix/skills/test.md
   Write regression tests and run the full suite.
   If tests fail, revise and retest (up to 5 iterations).

5. Read and execute .ai-workflows/bugfix/skills/review.md
   Self-review your changes. If issues found, correct them,
   retest, and re-review (up to 4 iterations).

6. Write PR title and description to .ai-session/pr.md.
   Use the ## Title heading format. Include a Root Cause section.

Placement: your-repo/.ai-bot/new-ticket-workflow.md

Applies to: New tickets only (not PR feedback)

Requires: The .ai-workflows/ skill files to be available. See Level 4 for importing them.

3 .ai-bot/feedback-workflow.md — PR feedback handling

Structures how the AI handles PR review comments. The AI recovers context from the original session, makes targeted changes, and updates session artifacts.

Why it matters: Without this, the AI treats each feedback round as a fresh problem. With it, the AI reads prior session context (diagnosis, implementation notes, test strategy) and makes coherent follow-up changes.

Example content

1. Read .ai-session/session-context.md to recover prior decisions.
2. Read .ai-session/diagnosis.md and .ai-session/implementation-notes.md.
3. Address each review comment. For each:
   - Understand the reviewer's concern
   - Make the minimal change that addresses it
   - Verify the change doesn't break existing tests
4. Run validation commands (`make build`, `make test`).
5. Update .ai-session/session-context.md with a summary of this round.
6. Write .ai-session/comment-responses.json.

Placement: your-repo/.ai-bot/feedback-workflow.md

Applies to: PR feedback only (not new tickets)

4 .ai-bot/config.yaml — Imports, validation, PR settings

Bot-level configuration for the repository. Controls PR creation behavior, declares shared repos to import, and provides AI-readable validation commands.

Why it matters: Imports let you share workflow skill files across many repositories. One central ai-workflows repo can serve all your projects.

Example content

# Clone shared workflow skills into the workspace
imports:
  - repo: https://github.com/your-org/ai-workflows
    path: .ai-workflows
    ref: main
    install: .ai-workflows/install.sh

# Validation commands (hints for the AI)
validation_commands:
  - make build
  - make test
  - make lint

# PR creation settings
pr:
  draft: true
  title_prefix: "[AI]"
  labels:
    - ai-generated
    - needs-review

# AI tool restrictions
ai:
  claude:
    allowed_tools: "Bash Edit Read Write"

Placement: your-repo/.ai-bot/config.yaml

Applies to: Bot behavior (imports run before AI, PR settings apply after)

5 .ai-bot/container.json — Custom container image

Specify a custom container image with your exact toolchain pre-installed. Faster startup, deterministic environment, no "install during AI session" overhead.

Why it matters: A generic ubuntu:latest image means the AI spends tokens installing Go, Python, Node, etc. A pre-built dev image means the AI starts coding immediately.

Example content

{
  "image": "your-org/dev-environment:latest",
  "postCreateCommand": "make setup",
  "env": {
    "GOPATH": "/go",
    "LANG": "en_US.UTF-8"
  },
  "resourceLimits": {
    "memory": "16g",
    "cpus": "4"
  }
}

Placement: your-repo/.ai-bot/container.json

Alternative: .devcontainer/devcontainer.json (standard format, subset supported)

What the AI sees: before vs after

No repo config (default)

The AI receives only the standard instructions. It must discover build tools, test commands, and coding conventions from the repository itself. Results are unpredictable.

  • May run wrong build commands
  • May skip tests entirely
  • No structured problem-solving
  • No self-review phase
  • Generic PR descriptions
  • No session continuity for feedback
With repo config (Levels 1-4)

The AI receives specific validation commands, a structured workflow, and shared skill files. Results are consistent and high-quality.

  • Runs exact build/test/lint commands
  • Follows multi-phase workflow
  • Writes diagnosis before fixing
  • Self-reviews with iteration caps
  • Generates structured PR descriptions
  • Maintains session context across rounds

11. Using a Local Model (Detailed Setup)

Replace the cloud AI with your own model server

The bot never calls the AI API directly — it sets environment variables, and the CLI inside the container reads them. "Use a local model" means: run a model server on your machine and tell the CLI to connect there instead of the cloud. The key constraint is API compatibility — the CLI expects a specific request/response format.

Option A Anthropic Messages API server (Ollama, vLLM, LiteLLM)

If your local server implements the Anthropic Messages API (POST /v1/messages with streaming SSE), Claude Code CLI can talk to it natively.

1. Start the model server

# Example with Ollama (requires anthropic-compatible mode)
ollama serve

# Example with vLLM
vllm serve your-model-name --api-format anthropic --port 8000

# Example with LiteLLM proxy
litellm --model ollama/llama3.1 --port 4000

2. Configure the bot

# config.yaml
ai_provider: "claude"

claude:
  proxy_url: "http://host.containers.internal:8000"
  proxy_auth_token: "dummy"      # required by config validation, but not sent to local server
  proxy_vertex_format: false    # direct connection, no URL rewriting

This sets ANTHROPIC_BASE_URL=http://host.containers.internal:8000 inside the container. The Claude Code CLI sends all requests there instead of api.anthropic.com.

3. Network flow

Container (Claude Code CLI) → http://host.containers.internal:8000 # podman host resolution → Your Machine (model server listening on :8000) → GPU (local inference)
Requirements
  • Server must support streaming SSE responses in Anthropic Messages API format
  • Server must handle the model field in requests (map it to your local model)
  • host.containers.internal resolves to the host machine from inside podman containers
  • For Docker, use host.docker.internal instead
Option B OpenAI-compatible server (via Gemini path)

If your local server implements the OpenAI Chat Completions API (POST /v1/chat/completions), you can use the Gemini provider path.

1. Start the model server

# Example with Ollama (OpenAI-compatible by default)
ollama serve   # listens on :11434, serves /v1/chat/completions

# Example with vLLM
vllm serve your-model --port 8000   # OpenAI-compatible by default

# Example with llama.cpp server
./llama-server -m model.gguf --port 8080

2. Configure the bot

# config.yaml
ai_provider: "gemini"

gemini:
  api_key: "dummy"               # required but ignored by local server
  model: "your-local-model-name"

The Gemini CLI reads GEMINI_API_KEY and sends requests in OpenAI-compatible format. You may need to configure the base URL via the container image or environment variable overrides.

3. Network flow

The Gemini CLI may have specific expectations about response format (tool use, function calling) that simpler servers don't fully support. Option A (Claude path) is more battle-tested for agentic use cases.

Option C Fully custom CLI provider

Build your own container image with a CLI tool that replaces both Claude Code and Gemini CLI entirely. Full control over the AI integration.

1. Build your CLI tool

Your tool must:

  1. Accept -p "prompt text" as a command-line argument
  2. Read /workspace/.ai-session/task.md from the prompt
  3. Call your local model API however you want
  4. Edit files in /workspace/
  5. Optionally write /workspace/.ai-session/pr.md
  6. Exit with code 0 on success, non-zero on failure

2. Configure the bot

# config.yaml
ai_provider: "my-tool"

# Container image that has your CLI installed
container:
  default_image: "your-org/ai-worker:latest"

The bot's fallback command is:
my-tool -p "Read /workspace/.ai-session/task.md and complete the task described there."

3. Network flow

Container (your custom CLI: my-tool) → whatever your tool does internally → http://host.containers.internal:PORT # your model server → GPU or CPU (inference)

This gives you total control. Any language, any model, any API. The bot doesn't care what happens inside the container as long as files are edited and the process exits cleanly.

Host resolution from containers

Networking How the container reaches your host machine

Containers run in an isolated network. To reach a server on the host machine, use these special hostnames:

Podman
host.containers.internal
Resolves automatically in rootless podman. For rootful podman, add --network=slirp4netns.
Docker
host.docker.internal
Works on Docker Desktop (macOS/Windows). On Linux Docker, add --add-host=host.docker.internal:host-gateway.
